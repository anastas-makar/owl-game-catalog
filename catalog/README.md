# Как добавлять игровые сущности

В этой директории находятся исходные JSON-файлы игрового каталога.

## Обычный порядок работы

1. Найдите директорию нужной категории.
2. Прочитайте её `README.md`.
3. Скопируйте ближайший по смыслу существующий JSON-файл.
4. Измените `templateId`, отображаемые данные и ссылки.
5. Не добавляйте поля, которых нет в актуальном import DTO.
6. Запустите проверку.
7. Откройте pull request в `develop`.

Автору игрового контента не требуется доступ к `main`, production-серверу или основному S3.

## Структура

```text
catalog/
  buildings/
  enemies/
  furniture/
  garden-items/
  locations/
  maps/
  medals/
  plants/
  pouches/
  quests/
  recipes/
  supplies/
```

Один исходный файл содержит одну корневую сущность.

Мешочки — исключение только по смыслу, но не по формату хранения: каждый JSON в `pouches/` описывает один декоративный шаблон изображения. Шаблоны мешочков не являются объектами игрового мира. 

```text
buildings/stone-fortress.json
furniture/red-sofa.json
quests/first-hatches.json
```

Имя файла должно совпадать с корневым `templateId`.

## Общие требования к JSON

Файл должен:

* содержать один JSON-объект в корне;
* использовать UTF-8;
* использовать двойные кавычки;
* не содержать комментариев и завершающих запятых;
* иметь корневой `templateId`;
* соответствовать актуальному import DTO;
* не содержать `id`, `releaseId` и UUID пользовательских объектов.

Правильно:

```json
{
  "templateId": "red-sofa",
  "name": "Красный диван"
}
```

Неправильно:

```json
{
  "templateId": "Red_Sofa_v2",
  "id": "0f88d63c-...",
  "releaseId": "..."
}
```

## Идентификаторы

Корневые `templateId` записываются в kebab-case:

```text
stone-fortress
swamp-ghoul
red-sofa
```

После публикации идентификатор сохраняется, даже если название объекта изменилось.

Вложенные элементы могут использовать `templateId`, `slotId`, `endingId` или номер страницы. Используйте поле, которое предусмотрено моделью соответствующей категории.

## Тексты

Текущий каталог русскоязычный. Названия, описания и текст кнопок пишутся по-русски.

Технические идентификаторы, enum-значения и теги пишутся в формате, принятом в backend.

## Изображения

Не добавляйте изображение непосредственно в Git.

Если картинка уже находится в основном хранилище, укажите:

```json
{
  "imageKey": "furniture/red-sofa.webp"
}
```

Если у вас нет доступа к хранилищу, передайте временную публичную ссылку:

```json
{
  "sourceImageUrl": "https://example.org/my-red-sofa.png"
}
```

Перед слиянием изменений в `main` сопровождающий проекта проверит изображение, загрузит его в основное S3 и заменит `sourceImageUrl` на `imageKey`.

Не указывайте оба поля одновременно. Не используйте `imageUrl` в исходном каталоге.

## Источники получения

У сущностей, которые могут выдаваться игроку, может быть поле `allowedAcquisitionSources`.

Это белый список способов получения сущности:

```json
{
  "allowedAcquisitionSources": [
    "POUCH",
    "SHOP"
  ]
}
```

Поле имеет следующую семантику:

* если поле отсутствует или равно `null`, ограничений нет: сущность можно получать любым поддерживаемым способом;
* если указан пустой список, сущность нельзя получить ни одним стандартным способом;
* если указан непустой список, сущность можно получить только перечисленными способами.

Доступные источники:

* `POUCH` — сущность может случайно выпасть из мешочка;
* `SHOP` — сущность может появиться в лавке торговца;
* `QUEST_REWARD` — сущность может быть выдана как награда за завершение квеста;
* `EXPEDITION_REWARD` — сущность может быть выдана после победы в экспедиции и освобождения карты.

Пример обычной сущности без ограничений:

```json
{
  "templateId": "pumpkin-soup"
}
```

Пример рецепта, который можно найти только в мешочке и лавке:

```json
{
  "templateId": "pumpkin-soup",
  "allowedAcquisitionSources": [
    "POUCH",
    "SHOP"
  ]
}
```

Пример сущности, доступной только как награда за квест:

```json
{
  "templateId": "ancient-potion",
  "allowedAcquisitionSources": [
    "QUEST_REWARD"
  ]
}
```

Пример сущности, которая пока не выдаётся игроку стандартными способами:

```json
{
  "templateId": "unfinished-recipe",
  "allowedAcquisitionSources": []
}
```

При добавлении нового источника обычные сущности без поля `allowedAcquisitionSources` автоматически считаются доступными через него. Сущности с явно заданным белым списком остаются доступными только через перечисленные источники.

Квестовая награда описывается в `lootBundle` конечной страницы квеста. Подробнее см. в [документации квестов](quests/README.md#лут).

Большинство сущностей можно получать любым способом, поэтому поле ограничения обычно не нужно.



## Ссылки между сущностями

Поля вида:

```text
questTemplateId
supplyTemplateId
fixedLocationTemplateId
completionMedalTemplateId
```

должны ссылаться на существующий `templateId` нужной категории.

## Проверка

Запускайте проверку из корня репозитория.

В Windows:

```bat
.\scripts\validate-catalog.bat
```

В Linux:

```bash
sh ./scripts/validate-catalog.sh
```

Если `validate-catalog.sh` имеет право на выполнение:

```bash
./scripts/validate-catalog.sh
```

Эта проверка соответствует работе с `develop` и разрешает временные `sourceImageUrl`.

Строгая проверка перед `main` выполняется сопровождающим проекта.

## Версия формата каталога

Текущая версия схемы каталога: **1**.

Версия схемы изменяется, когда меняются структура JSON, обязательные поля или правила обработки данных так, 
что существующие файлы каталога, backend или клиент требуют изменений.

История изменений находится в [`CHANGELOG.md`](CHANGELOG.md).
