# Как вносить изменения в каталог Owl Game

Этот репозиторий содержит исходные данные игрового каталога Owl Game.

Каталог хранится в виде отдельных JSON-файлов. Итоговый файл релиза собирается и проверяется автоматически. Сгенерированный файл релиза не следует редактировать вручную.

## Порядок работы

Обычный порядок внесения изменений:

1. Создать рабочую ветку от `develop`.
2. Добавить или изменить JSON-файлы каталога.
3. Запустить локальную сборку и проверку каталога.
4. Создать pull request в `develop`.
5. Дождаться успешного выполнения всех проверок.
6. После проверки изменений слить `develop` в `main`.
7. Для выпуска каталога создать и отправить тег формата `catalog-vX.Y.Z`.

Пример:

```bash
git checkout develop
git pull --ff-only origin develop

git checkout -b catalog/add-stone-fortress

git add .
git commit -m "Add stone fortress catalog items"
git push -u origin catalog/add-stone-fortress
```

Изменения не следует отправлять непосредственно в `main`, кроме исправлений, для которых прямой push был заранее осознанно выбран.

## Структура каталога

Каждая корневая сущность хранится в отдельном JSON-файле в каталоге соответствующего типа.

Примерная структура:

```text
buildings/
enemies/
furniture/
garden-items/
locations/
maps/
medals/
plants/
quests/
recipes/
supplies/
```

Один файл должен содержать одну корневую сущность.

Например:

```text
buildings/stone-fortress.json
furniture/red-sofa.json
supplies/honey.json
```

Не следует объединять несколько зданий, предметов мебели или других корневых сущностей в одном исходном файле.

## Требования к JSON

Файлы должны содержать корректный JSON:

* без комментариев;
* без завершающих запятых;
* в кодировке UTF-8;
* с двойными кавычками для имён полей и строк;
* с полями, соответствующими актуальным import DTO backend;
* без MongoDB-полей `id` и `releaseId`.

Не следует добавлять поля «на будущее», если backend их пока не поддерживает. Неизвестные поля могут скрыть ошибку проектирования или создать ложное впечатление, что соответствующая функция уже реализована.

## Правила для templateId

Каждая корневая сущность должна иметь `templateId`.

```json
{
  "templateId": "stone-fortress",
  "name": "Каменный замок"
}
```

`templateId` должен:

* состоять из латинских строчных букв, цифр и дефисов;
* быть понятным человеку;
* быть уникальным;
* оставаться стабильным после публикации;
* не содержать названия окружения, номера релиза или MongoDB ID.

Правильно:

```text
stone-fortress
red-sofa
swamp-ghoul
old-grotto
```

Неправильно:

```text
StoneFortress
stone_fortress
building-1
stone-fortress-v2
prod-red-sofa
```

После первого опубликованного релиза изменение `templateId` следует рассматривать как удаление старой сущности и создание новой. Поэтому переименовывать опубликованные идентификаторы без необходимости нельзя.

## Вложенные сущности

Вложенные самостоятельные элементы также должны иметь `templateId`.

Это относится, в частности, к:

* комнатам;
* садам;
* сценам;
* этапам и развязкам квестов, если их модель предусматривает `templateId`;
* другим объектам, находящимся в массивах.

Для вложенных элементов следует использовать идентификатор родителя как префикс.

Пример:

```json
{
  "templateId": "stone-fortress",
  "rooms": [
    {
      "templateId": "stone-fortress-main-hall",
      "name": "Главный зал",
      "roomNumber": 1
    },
    {
      "templateId": "stone-fortress-kitchen",
      "name": "Кухня",
      "roomNumber": 2
    }
  ]
}
```

Такой формат уменьшает риск случайного совпадения идентификаторов:

```text
stone-fortress-main-hall
wooden-house-main-hall
```

Порядковые номера вроде `roomNumber`, `gardenNumber` и `sceneNumber` не заменяют `templateId`. Номер отвечает за порядок отображения, а `templateId` — за устойчивую идентификацию сущности.

## Названия файлов

Имя файла должно соответствовать `templateId` корневой сущности.

Пример:

```text
buildings/stone-fortress.json
```

```json
{
  "templateId": "stone-fortress"
}
```

Следует использовать расширение `.json` только для файлов, которые должны попасть в сборку релиза.

Экспериментальные данные можно хранить с расширением `.json.draft`:

```text
drafts/quests/first-hatches.json.draft
```

Сборщик не должен включать файлы `.json.draft` в итоговый релиз.

## Тексты и локализация

Текущая версия каталога предназначена для русскоязычных пользователей.

Пользовательские поля следует писать по-русски:

```json
{
  "name": "Каменный замок",
  "description": "Старый замок с высокой башней"
}
```

Не следует самостоятельно менять строковые поля на объекты локализации:

```json
{
  "name": {
    "ru": "Каменный замок",
    "en": "Stone Castle"
  }
}
```

Полноценная локализация должна вводиться отдельным изменением схемы, import DTO, валидатора и клиента. До этого момента обычные строковые поля считаются русскоязычными.

## Теги

Поле `tags` следует добавлять только в те сущности, где оно уже присутствует в актуальной модели backend и действительно используется игровой логикой.

Не следует заранее добавлять теги всем сущностям только ради возможного будущего использования.

Если теги поддерживаются моделью:

* используйте латинские стабильные значения;
* не используйте отображаемые пользователю русские фразы в качестве технических тегов;
* не дублируйте тип сущности без необходимости.

Пример:

```json
{
  "tags": [
    "swamp",
    "undead",
    "night"
  ]
}
```

## Изображения

Изображения хранятся отдельно в S3. В каталоге должна находиться только ссылка или ключ изображения в соответствии с актуальной моделью.

Пример:

```json
{
  "imageUrl": "https://storage.example.com/owl-game/buildings/stone-fortress.webp"
}
```

Перед pull request необходимо проверить:

* ссылка ведёт на существующий объект;
* объект доступен клиенту;
* сервер возвращает правильный `Content-Type`;
* имя объекта не содержит случайных пробелов;
* регистр символов в URL совпадает с именем объекта;
* изображение имеет подходящий для мобильного приложения размер.

Не следует использовать временные адреса вроде:

```text
https://example.invalid/...
```

в релизной ветке.

## Ссылки между сущностями

Все ссылки вида `questId`, `enemyId`, `locationId`, `templateId` и аналогичные должны указывать на существующие сущности каталога.

Для ссылок следует использовать технический идентификатор, а не отображаемое имя.

Правильно:

```json
{
  "questId": "first-hatches"
}
```

Неправильно:

```json
{
  "questId": "Первые люки"
}
```

Удалять сущность, на которую ссылаются другие файлы, можно только одновременно с исправлением всех ссылок.

## Enum-значения

Значения полей типа `type`, `gardenType`, `rewardType` и аналогичных должны точно совпадать с Java enum в backend.

Например:

```json
{
  "type": "HOUSE"
}
```

Регистр имеет значение. Не следует придумывать новое enum-значение только в JSON. Сначала необходимо добавить его в backend, обновить импортную модель и валидатор.

## Квесты и награды

Структуру особого лута за развязки квестов следует добавлять только после определения единого формата в backend.

До утверждения схемы экспериментальные квесты можно хранить в `drafts` с расширением `.json.draft`.

Нельзя использовать `endingId` одновременно как:

* идентификатор развязки;
* идентификатор предмета;
* неявный идентификатор таблицы лута.

Развязка и выдаваемая награда должны быть разделены явными полями модели. Например, после утверждения схемы развязка может ссылаться на награду или таблицу лута отдельным идентификатором.

## Проверка перед pull request

Перед отправкой изменений необходимо запустить ту же команду, которая используется в GitHub Actions на шаге:

```text
Build and validate catalog
```

Проверка должна завершаться без ошибок и предупреждений о:

* пропущенных `templateId`;
* дублирующихся идентификаторах;
* отсутствующих ссылках;
* неизвестных enum-значениях;
* неверной структуре JSON;
* несовпадении схемы;
* отсутствующих обязательных полях.

Также следует проверить список изменённых файлов:

```bash
git status
git diff --check
git diff --stat
```

Не следует исправлять ошибку валидатора удалением проверки, если сами данные действительно неполны.

## Pull request

В pull request следует кратко указать:

* какие сущности добавлены или изменены;
* какие изображения были загружены;
* появились ли новые ссылки между сущностями;
* требуется ли соответствующее изменение backend или Android-клиента;
* меняется ли структура данных.

Пример описания:

```text
Добавлен каменный замок:

- четыре комнаты;
- сад, огород и пруд;
- ссылки на изображения в S3;
- новый диван для главного зала.

Схема каталога и enum-значения не изменялись.
```

## Выпуск релиза

Релиз каталога создаётся только из проверенного состояния ветки `main`.

Формат тега:

```text
catalog-vMAJOR.MINOR.PATCH
```

Пример:

```bash
git checkout main
git pull --ff-only origin main

git tag -a catalog-v0.1.0 -m "Initial catalog release"
git push origin catalog-v0.1.0
```

Опубликованный тег не следует перемещать на другой commit. При исправлении данных нужно создать новый commit и новый тег:

```text
catalog-v0.1.1
```

## Изменения схемы

До первого производственного релиза и появления пользователей схему разрешается менять свободно, включая полное удаление тестовой базы.

После появления опубликованных данных и пользовательского состояния необходимо учитывать:

* совместимость старых клиентов;
* стабильность `templateId`;
* сохранённые игровые сущности пользователей;
* миграцию MongoDB;
* изменение `schemaVersion`;
* возможность повторного импорта релиза.

Изменения схемы после первого релиза должны оформляться отдельно от обычного добавления контента.

## Контрольный список

Перед отправкой pull request проверьте:

* [ ] Один корневой объект находится в одном JSON-файле.
* [ ] Имя файла совпадает с корневым `templateId`.
* [ ] Все корневые и вложенные сущности имеют `templateId`.
* [ ] Все `templateId` написаны в kebab-case.
* [ ] В JSON нет `id` и `releaseId`.
* [ ] Все enum-значения существуют в backend.
* [ ] Все ссылки ведут на существующие сущности.
* [ ] Временные URL изображений заменены на реальные.
* [ ] Черновики имеют расширение `.json.draft`.
* [ ] Локальная сборка и валидация прошли успешно.
* [ ] Изменения отправляются через pull request в `develop`.
