# Сопровождение каталога Owl Game

Этот документ предназначен прежде всего для владельца репозитория и разработчиков backend. Инструкции для авторов игрового контента находятся в [`catalog/README.md`](catalog/README.md) и в `README.md` соответствующих категорий.

Текущая версия схемы каталога задаётся константой `CATALOG_SCHEMA_VERSION` в [`scripts/build\_catalog.py`](scripts/build_catalog.py).

Изменения структуры каталога, правил валидации и требований к контрибьюторам фиксируются в [`catalog/CHANGELOG.md`](catalog/CHANGELOG.md).

## Версии каталога

У каталога есть два разных понятия версии.

### Версия релиза

Версия релиза описывает конкретную опубликованную сборку содержимого каталога.

Она передаётся сборщику через:

```text
--version
```

Для production-релиза версия берётся из имени Git-тега:

```text
catalog-v0.1.0
```

Изменение игрового содержимого — например, добавление новых врагов, мебели или квестов — может приводить к новому релизу без изменения схемы каталога.

### Версия схемы

`schemaVersion` описывает формат каталога: структуру JSON, обязательные поля и правила, с которыми должны быть совместимы backend и клиент.

Текущая версия схемы задаётся непосредственно в коде:

```python
CATALOG_SCHEMA_VERSION = 1
```

Контрибьютор не передаёт `schemaVersion` через командную строку и не выбирает её самостоятельно.

При несовместимом изменении формата необходимо одновременно:

* изменить `CATALOG_SCHEMA_VERSION`;
* обновить import DTO и связанные backend-модели;
* обновить Python-валидатор;
* при необходимости обновить Android-клиент;
* обновить документацию;
* описать изменение в [`catalog/CHANGELOG.md`](catalog/CHANGELOG.md).

Мелкие исправления текста документации, уточнения формулировок и другие изменения, не меняющие контракт каталога, не требуют повышения `schemaVersion`.

## Ветки и путь изменения

Обычный путь изменения:

1. Рабочая ветка создаётся от `develop`.
2. Автор открывает pull request в `develop`.
3. В `develop` допускаются временные внешние ссылки `sourceImageUrl`.
4. Перед слиянием `develop` в `main` изображения проверяются и переносятся в основное S3-хранилище.
5. Все `sourceImageUrl` заменяются на `imageKey`.
6. Pull request или push в `main` проходит строгую проверку с `--require-image-keys`.
7. Релизный тег `catalog-vX.Y.Z` создаётся только на commit, входящем в `main`.
8. Workflow собирает и публикует итоговый `catalog-release.json`.

Пример рабочей ветки:

```bash
git checkout develop
git pull --ff-only origin develop

git checkout -b catalog/add-stone-fortress
```

## Сборка и проверка

Обычная локальная проверка, соответствующая работе с `develop`:

```bash
python scripts/build\_catalog.py \\
  --catalog-dir catalog \\
  --output build/catalog-release.json \\
  --version dev-local \\
  --commit-sha local
```

Строгая проверка перед `main` и релизом:

```bash
python scripts/build\_catalog.py \\
  --catalog-dir catalog \\
  --output build/catalog-release.json \\
  --version dev-local \\
  --commit-sha local \\
  --require-image-keys
```

`schemaVersion` указывать не нужно: сборщик берёт его из `CATALOG\_SCHEMA\_VERSION`.

Сгенерированный `build/catalog-release.json` не редактируется вручную.

## Изображения

Каталог поддерживает два поля, но они используются на разных этапах.

### sourceImageUrl

Временная публичная ссылка на изображение автора pull request:

```json
{
  "sourceImageUrl": "https://example.org/generated/castle.png"
}
```

Это поле допустимо в рабочей ветке и `develop`. Автору не нужен доступ к основному S3.

Перед использованием изображения следует вручную проверить:

* что ссылка открывается без авторизации;
* что файл действительно является изображением;
* что автор имеет право передать его проекту;
* что изображение соответствует содержанию сущности;
* что в нём нет случайного текста, водяных знаков и нежелательных деталей;
* что размер и формат подходят мобильному приложению.

Не следует автоматически скачивать произвольные ссылки из внешних pull request с использованием production-секретов.

### imageKey

Постоянный ключ объекта в основном S3:

```json
{
  "imageKey": "buildings/stone-fortress.webp"
}
```

В `main`, релизном теге и MongoDB-каталоге должен храниться только `imageKey`. Полный публичный URL собирается backend из базового адреса хранилища и ключа объекта.

Одновременно `sourceImageUrl` и `imageKey` у одного объекта указывать нельзя.

Поле `imageUrl` в исходном каталоге не используется. Оно может присутствовать только в API-ответе, который backend готовит для клиента.

## Идентификаторы

### Корневые шаблоны

Каждая корневая сущность имеет `templateId`, уникальный в пределах своей категории:

```json
{
  "templateId": "stone-fortress"
}
```

`templateId`:

* записывается в kebab-case;
* остаётся стабильным после публикации;
* не содержит номера релиза, окружения или UUID пользователя;
* после публикации не переименовывается без осознанной миграции.

### Вложенные элементы

Вложенные элементы используют идентификатор, предусмотренный моделью:

|Родитель|Поле|Идентификатор|
|-|-|-|
|здание|`rooms`|`templateId`|
|здание|`gardens`|`templateId`|
|локация|`scenes`|`templateId`|
|карта|`locationSlots`|`slotId`|
|карта|`enemySlots`|`slotId`|
|квест|`pages`|`number`|
|развязка квеста|конечная страница|`endingId`|

Вложенный идентификатор должен быть стабильным и уникальным в пределах родителя. Его сохранение позволяет отличить редактирование существующего элемента от удаления старого и добавления нового.

### Экземпляры игрока

UUID зданий, комнат и других объектов игрока не относятся к каталогу. У игрока могут существовать несколько экземпляров одного `templateId`, каждый со своим UUID.

## Источники получения

У выдаваемых сущностей может быть необязательное поле `allowedAcquisitionSources`.

Отсутствующее поле или `null` означает отсутствие ограничений:

```json
{
  "templateId": "wooden-chair"
}
```

Белый список ограничивает способы получения:

```json
{
  "templateId": "quest-sword",
  "allowedAcquisitionSources": \[
    "QUEST\_REWARD"
  ]
}
```

Пустой список означает, что сущность нельзя получить ни через один стандартный источник:

```json
{
  "templateId": "unfinished-statue",
  "allowedAcquisitionSources": \[]
}
```

Значения должны соответствовать текущему enum backend. При добавлении нового источника обычные сущности без белого списка автоматически считаются доступными через него.

## Локализация

Текущий каталог русскоязычный. Отображаемые пользователю поля хранят обычные русские строки:

```json
{
  "name": "Каменный замок"
}
```

Переход к структурам вида `{"ru": "...", "en": "..."}` должен выполняться отдельным изменением схемы, DTO, валидатора, backend и Android-клиента.

## Теги

Теги добавляются только в модели, которые их реально поддерживают. Не следует распространять `tags` на все сущности заранее.

Технические теги рекомендуется писать латинскими строчными буквами:

```json
{
  "tags": [
    "swamp",
    "undead"
  ]
}
```

Новые значения должны иметь понятную игровую семантику и использоваться генератором, фильтрацией или другим кодом.

## Квестовый лут

Лут хранится в конечной странице квеста через `lootBundle`.

Каждый присутствующий пул разыгрывается независимо:

* отсутствие пула означает, что эта категория ничего не выдаёт;
* отсутствие `dropChance` означает гарантированное выпадение;
* `dropChance: 0.5` означает вероятность 50%;
* `templateIds: null` или отсутствие поля означает выбор любого разрешённого шаблона категории;
* непустой `templateIds` ограничивает выбор перечисленными шаблонами;
* пустой `templateIds` считается ошибкой каталога;
* отсутствие `amount` трактуется сервисом как `1`, если это соответствует текущей backend-реализации.

Награда должна ссылаться только на существующие шаблоны, доступные через `QUEST_REWARD`.

`lootAvailable` не является частью каталога. Это состояние конкретного игрока: есть ли у него право забрать награду сейчас.

## Изменение схемы

До первого production-релиза и появления пользователей схему можно менять свободно, включая удаление тестовой базы.

После публикации следует учитывать:

* совместимость старых клиентов;
* стабильность идентификаторов;
* уже созданные пользовательские экземпляры;
* миграции MongoDB;
* изменение `CATALOG_SCHEMA_VERSION`;
* повторный импорт релиза;
* поведение старых квестов и уже полученных наград.

Изменение DTO, каталожных моделей, mapper, Python-валидатора и документации выполняется одним согласованным изменением.

Если изменение меняет формат JSON, обязательность полей или другие правила совместимости, необходимо решить, требует ли оно повышения `CATALOG_SCHEMA_VERSION`.

Все заметные изменения формата и правил каталога следует записывать в раздел `Unreleased` файла [`catalog/CHANGELOG.md`](catalog/CHANGELOG.md). При выпуске новой версии схемы накопленные записи переносятся в раздел соответствующей версии.

## Проверка pull request

Перед слиянием проверьте:

* JSON проходит сборку;
* имя файла совпадает с корневым `templateId`;
* ссылки ведут на существующие шаблоны;
* enum-значения существуют в backend;
* вложенные идентификаторы уникальны;
* `sourceImageUrl` допустим только до `main`;
* перед `main` все изображения перенесены в S3;
* новые поля поддержаны import DTO, Mongo-моделью и mapper;
* Python-валидатор знает о новых ссылках и ограничениях;
* при изменении схемы обновлён `CATALOG_SCHEMA_VERSION`;
* заметные изменения формата или правил внесены в `catalog/CHANGELOG.md`;
* документация нужной категории обновлена.

## Выпуск релиза

Релиз создаётся из проверенного состояния `main`:

```bash
git checkout main
git pull --ff-only origin main

git tag -a catalog-v0.1.0 -m "Initial catalog release"
git push origin catalog-v0.1.0
```

Имя тега становится `version` опубликованного `catalog-release.json`.

`schemaVersion` при этом берётся из `CATALOG_SCHEMA_VERSION` и не зависит от номера релизного тега.

Например, релизы `catalog-v0.1.0`, `catalog-v0.1.1` и `catalog-v0.2.0` могут использовать одну и ту же версию схемы, если формат каталога между ними не менялся.

Опубликованный тег не перемещается. Исправление выпускается новым commit и новым тегом, например `catalog-v0.1.1`.
