# Как вносить изменения в каталог Owl Game

Этот репозиторий содержит исходные данные игрового каталога Owl Game.

Каталог хранится в виде отдельных JSON-файлов. Итоговый файл релиза собирается и проверяется автоматически. Сгенерированный файл релиза не следует редактировать вручную.

## Порядок работы

Обычный порядок внесения изменений:

1. Создать рабочую ветку от `develop`.
2. Добавить или изменить JSON-файлы каталога.
3. Запустить локальную сборку и проверку каталога.
4. Создать pull request в `develop`.
5. Дождаться успешного выполнения всех проверок.
6. После проверки изменений слить `develop` в `main`.
7. Для выпуска каталога создать и отправить тег формата `catalog-vX.Y.Z`.

Пример:

```bash
git checkout develop
git pull --ff-only origin develop

git checkout -b catalog/add-stone-fortress

git add .
git commit -m "Add stone fortress catalog items"
git push -u origin catalog/add-stone-fortress
```

Изменения не следует отправлять непосредственно в `main`, кроме случаев, когда прямой push был выбран осознанно.

## Структура каталога

Каждая корневая сущность хранится в отдельном JSON-файле в каталоге соответствующего типа.

Примерная структура:

```text
buildings/
enemies/
furniture/
garden-items/
locations/
maps/
medals/
plants/
quests/
recipes/
supplies/
```

Один файл должен содержать одну корневую сущность.

Например:

```text
buildings/stone-fortress.json
furniture/red-sofa.json
supplies/honey.json
```

Не следует объединять несколько зданий, предметов мебели или других корневых сущностей в одном исходном файле.

## Требования к JSON

Файлы должны содержать корректный JSON:

* без комментариев;
* без завершающих запятых;
* в кодировке UTF-8;
* с двойными кавычками для имён полей и строк;
* с полями, соответствующими актуальным import DTO backend;
* без MongoDB-полей `id` и `releaseId`.

Не следует добавлять поля «на будущее», если backend их пока не поддерживает.

## Как размещать картинки

В pull request в develop изображение может быть указано через sourceImageUrl. 

Если изображение уже есть в хранилище, можно использовать его imageKey.

Перед слиянием изменений в main изображение должно быть проверено, 
загружено в основное хранилище, а sourceImageUrl заменён на imageKey. 

Релизный каталог не может содержать sourceImageUrl.

## Уровни идентификаторов

В проекте используются разные виды идентификаторов. Они не являются взаимозаменяемыми.

### UUID экземпляра игрока

Конкретные игровые объекты игрока имеют собственные UUID.

Например, у игрока могут быть два одинаковых замка:

```text
building UUID-1 → templateId stone-fortress
building UUID-2 → templateId stone-fortress
```

Это два разных игровых экземпляра, созданных по одному каталожному шаблону.

UUID пользовательских экземпляров не задаются в каталоге.

### templateId корневого шаблона

Каждая корневая сущность каталога должна иметь `templateId`.

```json
{
  "templateId": "stone-fortress",
  "name": "Каменный замок"
}
```

Корневыми шаблонами являются, например:

* здания;
* враги;
* мебель;
* локации;
* карты;
* медали;
* растения;
* квесты;
* рецепты;
* припасы.

`templateId` должен:

* состоять из латинских строчных букв, цифр и дефисов;
* быть понятным человеку;
* быть уникальным в пределах своей категории;
* оставаться стабильным после публикации;
* не содержать MongoDB ID, UUID экземпляра, номер релиза или название окружения.

Примеры:

```text
stone-fortress
red-sofa
swamp-ghoul
old-grotto
```

После публикации изменение корневого `templateId` следует рассматривать как удаление старого шаблона и создание нового.

### Идентификаторы вложенных элементов

Вложенные элементы используют идентификатор, предусмотренный их моделью.

Не существует общего правила, согласно которому любой вложенный объект обязан иметь `templateId`.

В текущей схеме используются следующие идентификаторы:

| Родитель | Вложенное поле  | Идентификатор |
| -------- | --------------- | ------------- |
| здание   | `rooms`         | `templateId`  |
| здание   | `gardens`       | `templateId`  |
| локация  | `scenes`        | `templateId`  |
| карта    | `locationSlots` | `slotId`      |
| карта    | `enemySlots`    | `slotId`      |
| квест    | `pages`         | `number`      |

Если в модели появятся `roomId`, `gardenId`, `endingId`, `sceneId` или другие предметные идентификаторы, валидатор и документацию следует обновить одновременно с DTO.

## Зачем нужны стабильные идентификаторы вложенных элементов

Каталожное здание хранится и импортируется целиком. Изменение одной кухни означает публикацию новой версии всего документа здания.

Тем не менее стабильный идентификатор комнаты позволяет различать два изменения.

Старый релиз:

```json
{
  "templateId": "stone-fortress",
  "rooms": [
    {
      "templateId": "kitchen",
      "name": "Кухня"
    }
  ]
}
```

Новый релиз:

```json
{
  "templateId": "stone-fortress",
  "rooms": [
    {
      "templateId": "kitchen",
      "name": "Большая кухня"
    }
  ]
}
```

Одинаковый идентификатор `kitchen` означает, что существующая комната была отредактирована.

Если `kitchen` исчезла и появилась `dining-room`, это означает удаление одной комнаты и добавление другой.

Такая идентификация полезна:

* при сравнении релизов;
* при миграции пользовательских данных;
* при анализе изменений каталога;
* для ссылок из других игровых сущностей;
* для сохранения связи между шаблоном и созданными игровыми экземплярами.

## Идентификаторы слотов

Слот не является самостоятельным шаблоном врага или локации.

Он описывает устойчивое место внутри родительской карты:

```json
{
  "slotId": "north-gate",
  "x": 0.25,
  "y": 0.4,
  "allowedTypes": [
    "UNDEAD"
  ],
  "requiredTags": [
    "weak"
  ]
}
```

Поэтому для слотов используется `slotId`, а не `templateId`.

Полная идентичность слота определяется родителем и локальным идентификатором:

```text
map templateId + slotId
```

Например:

```text
swamp-map / north-gate
```

Одинаковый `slotId` может использоваться в разных картах. В пределах одного массива слотов родительской карты идентификатор должен быть уникальным.

Если координаты или ограничения слота изменились, но `slotId` сохранился, это считается редактированием существующего слота.

Если старый `slotId` исчез и появился новый, это считается удалением одного слота и добавлением другого.

## Названия файлов

Имя файла должно соответствовать `templateId` корневой сущности.

Пример:

```text
buildings/stone-fortress.json
```

```json
{
  "templateId": "stone-fortress"
}
```

Расширение `.json` используется только для файлов, которые должны попасть в релиз.

Черновые данные можно хранить с расширением `.json.draft`:

```text
drafts/quests/first-hatches.json.draft
```

Сборщик не включает `.json.draft` в итоговый релиз.

## Тексты и локализация

Текущая версия каталога предназначена для русскоязычных пользователей.

Пользовательские поля следует писать по-русски:

```json
{
  "name": "Каменный замок",
  "description": "Старый замок с высокой башней"
}
```

Не следует самостоятельно превращать строковые поля в объекты локализации:

```json
{
  "name": {
    "ru": "Каменный замок",
    "en": "Stone Castle"
  }
}
```

Полноценная локализация должна вводиться отдельным изменением схемы, import DTO, валидатора и клиента.

До этого момента обычные строковые поля считаются русскоязычными.

## Теги

Поле `tags` следует добавлять только в те сущности, где оно присутствует в актуальной модели backend и используется игровой логикой.

Не следует заранее добавлять теги всем сущностям только ради возможного будущего применения.

Технические теги следует писать латинскими строчными буквами:

```json
{
  "tags": [
    "swamp",
    "undead",
    "night"
  ]
}
```

Теги не должны использоваться вместо основных типов и идентификаторов.

## Изображения

Изображения хранятся отдельно в S3. В каталоге находится только ссылка или ключ изображения в соответствии с актуальной моделью.

Пример:

```json
{
  "imageUrl": "https://storage.example.com/owl-game/buildings/stone-fortress.webp"
}
```

Перед pull request необходимо проверить:

* ссылка ведёт на существующий объект;
* объект доступен клиенту;
* сервер возвращает правильный `Content-Type`;
* регистр символов совпадает с именем объекта;
* изображение имеет подходящий для мобильного приложения размер;
* в релизном JSON не осталось временного адреса.

Не следует публиковать адреса вида:

```text
https://example.invalid/...
```

## Ссылки между сущностями

Ссылки на корневые сущности должны использовать их `templateId`.

Примеры таких полей:

```text
questTemplateId
supplyTemplateId
fixedLocationTemplateId
completionMedalTemplateId
```

Пример:

```json
{
  "fixedLocationTemplateId": "old-grotto"
}
```

Ссылка должна указывать на существующую сущность нужной категории.

Удалять шаблон, на который ссылаются другие файлы, можно только одновременно с исправлением всех ссылок.

## Enum-значения

Значения полей `type`, `gardenType`, `mode`, `rewardType` и аналогичных должны точно совпадать с Java enum в backend.

Например:

```json
{
  "type": "HOUSE"
}
```

Регистр имеет значение.

Новое enum-значение сначала добавляется в backend и import DTO, после чего используется в каталоге.

## Квесты и награды

Структуру особого лута за развязки квестов следует добавлять после определения единого формата в backend.

До утверждения схемы экспериментальные квесты можно хранить в `drafts` с расширением `.json.draft`.

Нельзя использовать `endingId` одновременно как:

* идентификатор развязки;
* идентификатор предмета;
* неявный идентификатор таблицы лута.

Развязка и награда должны быть разделены явными полями модели.

Если у развязки появится `endingId`, он должен быть стабильным и уникальным в пределах соответствующего квеста.

## Проверка перед pull request

Перед отправкой изменений необходимо запустить ту же сборку, которая используется в GitHub Actions на шаге:

```text
Build and validate catalog
```

Проверка должна завершаться без ошибок о:

* пропущенных корневых `templateId`;
* пропущенных вложенных `templateId` или `slotId`;
* повторяющихся идентификаторах;
* неизвестных ссылках;
* неверной структуре JSON;
* несуществующих страницах квеста;
* повторяющихся номерах страниц;
* отсутствующих обязательных полях.

Также следует проверить изменения Git:

```bash
git status
git diff --check
git diff --stat
```

Не следует исправлять ошибку валидатора простым удалением проверки, если данные действительно не соответствуют модели.

## Pull request

В pull request следует кратко указать:

* какие сущности добавлены или изменены;
* какие изображения загружены;
* появились ли новые ссылки между сущностями;
* изменились ли стабильные идентификаторы;
* требуется ли изменение backend или Android-клиента;
* меняется ли структура каталога.

Пример:

```text
Добавлен каменный замок:

- четыре комнаты;
- сад, огород и пруд;
- ссылки на изображения в S3;
- новый диван для главного зала.

Схема каталога и enum-значения не изменялись.
```

## Выпуск релиза

Релиз создаётся только из проверенного состояния ветки `main`.

Формат тега:

```text
catalog-vMAJOR.MINOR.PATCH
```

Пример:

```bash
git checkout main
git pull --ff-only origin main

git tag -a catalog-v0.1.0 -m "Initial catalog release"
git push origin catalog-v0.1.0
```

Опубликованный тег не следует перемещать на другой commit.

Для исправления данных создаются новый commit и новый тег:

```text
catalog-v0.1.1
```

## Изменения схемы

До первого производственного релиза и появления пользователей схему можно менять свободно, включая полное удаление тестовой базы.

После появления опубликованных данных и пользовательского состояния необходимо учитывать:

* стабильность корневых и вложенных идентификаторов;
* совместимость старых клиентов;
* созданные игровые экземпляры с UUID;
* миграцию MongoDB;
* изменение `schemaVersion`;
* возможность повторного импорта релиза.

Изменение имени стабильного идентификатора после первого релиза следует считать потенциально несовместимым изменением схемы.

## Контрольный список

Перед отправкой pull request проверьте:

* [ ] Один корневой объект находится в одном JSON-файле.
* [ ] Имя файла совпадает с корневым `templateId`.
* [ ] Каждая корневая сущность имеет `templateId`.
* [ ] Комнаты, сады и сцены имеют предусмотренный моделью `templateId`.
* [ ] Слоты карты имеют `slotId`.
* [ ] Идентификаторы вложенных элементов уникальны в пределах родителя.
* [ ] Стабильный идентификатор не был случайно заменён при обычном редактировании.
* [ ] В JSON нет MongoDB-полей `id` и `releaseId`.
* [ ] UUID пользовательских экземпляров не записаны в каталог.
* [ ] Все enum-значения существуют в backend.
* [ ] Все ссылки ведут на существующие сущности.
* [ ] Временные URL изображений заменены на реальные.
* [ ] Черновики имеют расширение `.json.draft`.
* [ ] Локальная сборка и валидация прошли успешно.
* [ ] Изменения отправляются через pull request в `develop`.
